# Карта проекта и контракт поведения

## Структура

| Файл | Ответственность | Уровень тестирования |
| --- | --- | --- |
| `src/components/Button.tsx` | Текст, клик, disabled, loading | Unit + RTL |
| `src/components/QuantityStepper.tsx` | Количество в диапазоне 1..max | Unit + RTL |
| `src/components/SearchField.tsx` | Управляемое поле поиска и очистка | Unit + RTL |
| `src/components/ProductCard.tsx` | Данные товара, доступность покупки | Unit + RTL |
| `src/components/CouponForm.tsx` | Проверка промокода | Unit + RTL |
| `src/components/CheckoutForm.tsx` | Валидация и отправка формы | Unit + RTL |
| `src/lib/money.ts` | Форматирование и расчёт суммы | Unit |
| `src/lib/validation.ts` | Правила формы | Unit |
| `src/lib/cart.ts` | Reducer и чтение сохранённой корзины | Unit |
| `src/lib/api.ts` | HTTP-клиент каталога и заказов | Unit |
| `src/features/Catalog.tsx` | Загрузка + поиск + категория + сортировка | Integration + RTL |
| `src/features/Cart.tsx` | Товары + счётчик + промокод + форма заказа | Integration + RTL |
| `src/App.tsx` | Связь каталога и корзины, localStorage | Integration + RTL |
| `server/shopApi.ts` | Учебный HTTP API | Используется в E2E |
| `server/products.json` | Шесть постоянных товаров | Данные для E2E |
| `src/test/fixtures.ts` | Один образец товара для ваших тестов | Вспомогательные данные |

Unit компонента — отрисовка одного компонента с props и проверка видимого поведения.
Integration — несколько настоящих компонентов вместе; подменять можно внешний API.
E2E — браузер, приложение и HTTP; ошибки и задержки можно моделировать через `cy.intercept`.

## Бизнес-правила — источник ожидаемого результата тестов

- Кнопка по умолчанию имеет `type="button"`. При `loading` текст «Подождите…», `aria-busy=true`, клики заблокированы.
- Счётчик принимает целые `value` и `max`, где `1 <= value <= max`. На границах соответствующая кнопка отключена.
  Он управляемый: вызывает `onChange`, а новое `value` передаёт родитель.
- Поиск по названию не зависит от регистра; пробелы по краям запроса игнорируются.
- Категория и поиск работают одновременно. Сортировка применяется к уже отфильтрованным товарам.
- Товар с нулевым остатком виден, но добавить его нельзя.
- Повторное добавление увеличивает количество существующей позиции; максимум — остаток товара.
- Уменьшение количества не удаляет товар: минимум 1. Для удаления есть отдельная кнопка.
- Сумма товаров = цена × количество. Цена хранится в целых гривнах (UAH).
- `DESK10` даёт 10% скидки от суммы товаров с округлением до целой гривны.
  Регистр и пробелы по краям не важны. Повторное применение не накапливает скидку.
  Неверный код после верного убирает скидку.
- Доставка стоит 300 ₴ при сумме товаров от 1 до 4999 ₴, бесплатна от 5000 ₴ **до скидки**.
  Для пустой корзины доставка и итог равны 0.
- Лампа × 1 = 4200 + 300 = **4500 ₴**. С DESK10: 4200 − 420 + 300 = **4080 ₴**.
  Лампа + блокнот = 5000, доставка 0; с DESK10 итог **4500 ₴**.
- Имя: минимум 2 символа после trim. Email: непустые части вокруг `@`, точка в домене, без пробелов.
  Адрес: минимум 10 символов после trim. Клиент показывает ошибки только после попытки отправить форму.
- При отправке заказа submit отключён. Ошибка сохраняет корзину и введённые поля; можно повторить отправку.
- Успешный заказ показывает номер, очищает корзину и сбрасывает промокод.
- Корзина сохраняется под ключом `deskshop.cart.v1`. Промокод и поля формы не сохраняются.
- Повреждённый JSON или не-массив в хранилище даёт пустую корзину; некорректные записи массива отбрасываются.
  Если запись в localStorage запрещена, корзина работает в текущей вкладке и показывает предупреждение.
- API не изменяет остатки и не хранит заказы. Это намеренная граница учебного приложения.

## HTTP

`GET /api/products` → 200 и массив `Product[]`.

`POST /api/orders` принимает JSON:

```json
{
  "customer": { "name": "Анна", "email": "anna@example.com", "address": "Учебная улица, 10" },
  "items": [{ "id": "lamp", "quantity": 1 }],
  "coupon": "DESK10"
}
```

Успех: 201, `{ "id": "DS-123456" }` (последние цифры времени; не проверяйте конкретный номер при реальном запросе).
Некорректный заказ: 400. Для проверки 500 и сетевых ошибок используйте заглушки.

## Подход к тестам

- Импортируйте `describe`, `it`, `expect`, `vi` из `vitest` явно.
- Для взаимодействий — `userEvent.setup()` и `await user.click/type(...)`.
- Для доступных элементов — `getByRole`, `getByLabelText`, `within`. Для появления после запроса — `findByRole`.
- В unit-тестах API можно использовать `vi.stubGlobal('fetch', ...)`; в integration — `vi.mock` модуля API
  или заглушку fetch. Создавайте свежие данные для каждого теста.
- Не подменяйте дочерние компоненты, reducer и вычисления в integration-тестах соответствующего поведения.
- Для управляемого компонента проверяйте callback или создавайте маленькую тестовую обёртку со state.
- Не используйте произвольные `sleep` / `cy.wait(1000)`, большие snapshots или CSS-классы как основной контракт.
- В форматированной цене есть неразрывные пробелы. Сравнивайте нормализованный текст либо ожидаемую строку
  с соответствующими пробелами; не вычисляйте expected той же функцией, которую тестируете.
